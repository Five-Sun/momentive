# 인증 (로그인/회원가입) 플랜

## 개요

`docs/specs/2026-08-27-auth.md`를 기반으로 이메일/비밀번호 회원가입·로그인·로그아웃과 JWT(Access+Refresh, rotation) 세션을 도입한다. 백엔드(Spring Security, JWT, refresh_token 테이블)와 프론트(로그인/회원가입 화면, AuthProvider, apiFetch 401 자동 refresh, 마이페이지 연동)가 함께 필요하지만, 백엔드 API 계약이 먼저 확정돼야 프론트 `apiFetch`/`AuthProvider`를 실제 응답 형태에 맞춰 구현할 수 있으므로 백엔드를 먼저 통합 완료하고, 그다음 프론트를 인프라(공통 배선) → 화면(로그인/회원가입) → 마이페이지 연동+회귀 순으로 쌓는다.

- **Phase 1 (백엔드 통합)**: `User`/`refresh_token` 엔티티, Spring Security, JWT 발급/검증, `/auth/*` API, `@CurrentUser`, CORS `allowCredentials(true)`까지 한 번에 통합해 백엔드만으로 API 계약이 완결되게 한다. 인증 도메인은 로그인-토큰검증-refresh-로그아웃이 서로 강하게 얽혀 있어 중간에 쪼개면 독립적으로 검증 가능한 마일스톤이 되지 않는다.
- **Phase 2 (프론트 인프라)**: `apiFetch`의 401 자동 refresh, `AuthProvider`, `auth.ts` API 클라이언트, `(shell)/layout.tsx`의 `/me` 선호출 배선을 화면 없이 먼저 완성해, 이후 화면 phase가 이 배선 위에서 로그인 상태만 소비하면 되게 한다.
- **Phase 3 (로그인/회원가입 화면)**: `/login`, `/signup` 화면을 구현해 회원가입→로그인 흐름 자체를 완결되게 검증한다.
- **Phase 4 (마이페이지 연동 + 회귀)**: 마이페이지 비로그인/로그인 UI 분기, 로그아웃 버튼을 붙이고, 기존 비로그인 허용 기능(상품 조회/장바구니/위시리스트)이 이번 변경으로 깨지지 않았는지 회귀를 확인한다.
- **Phase 5 (E2E 검증)**: Phase 4 통과 직후 `e2e-tester`가 spec의 사용자 시나리오를 도출해 실행한다.

`docs/backlog/2026-08-26-app-redesign-phase2-01.md`(검색 화면의 상태 분기 누락 사례)를 참고해, 로그인/비로그인 두 상태가 서로 배타적으로 조건화됐는지 Phase 3/4 구현 시 명시적으로 짚는다.

## Phase 1: 백엔드 인증 통합 (Spring Security + JWT + `/auth/*`)

이 phase가 끝나면 백엔드만으로 회원가입 → 로그인 → 인증된 API 호출 → 토큰 refresh → 로그아웃 전체 흐름을 curl/Postman 등으로 검증할 수 있는 상태가 된다.

- [x] `User` 엔티티(`id`, `email` unique, `password_hash`, `nickname`, `role`, `created_at`) 및 JPA Repository 추가. `@NoArgsConstructor(access = PROTECTED)` + 정적 팩토리로 생성.
- [x] `RefreshToken` 엔티티(`id`, `user_id` FK, `token_hash`, `expires_at`, `revoked_at`, `created_at`) 및 Repository 추가. 실제 토큰 값이 아닌 해시로 저장.
- [x] `AuthService`: 회원가입(이메일 중복 시 `EMAIL_ALREADY_EXISTS`), 로그인(실패 시 이메일 존재 여부와 무관하게 `INVALID_CREDENTIALS`로 통일), 로그아웃(refresh token revoke), refresh(rotation — 기존 토큰 무효화 후 신규 발급, 재사용/만료 시 `INVALID_REFRESH_TOKEN`) 로직 구현. `@Transactional` 경계는 Service에.
- [x] `AuthController`: `POST /auth/signup`(201), `POST /auth/login`(200), `POST /auth/logout`(204, 미인증 호출도 204), `POST /auth/refresh`(200), `GET /auth/me`(200/401) — spec 인터페이스의 request/response 필드와 에러 코드 그대로 구현. Access/Refresh는 httpOnly+Secure 쿠키(`SameSite=Lax`)로 `Set-Cookie`.
- [x] JWT 발급/검증 유틸(Access 30분, Refresh 14일) 및 커스텀 `OncePerRequestFilter` + `SecurityFilterChain` 구성. 인증 실패는 커스텀 `AuthenticationEntryPoint`로 기존 `ErrorResponse` 포맷 유지.
- [x] `@CurrentUser` 어노테이션 + `HandlerMethodArgumentResolver` 구현 — Service가 `SecurityContextHolder`에 직접 의존하지 않도록.
- [x] `USER`/`ADMIN` role 필드 반영(실제 admin 전용 API는 범위 밖, 필드/enum만 존재).
- [x] 비밀번호 해싱은 `BCryptPasswordEncoder` 사용.
- [x] `WebConfig`(`backend/src/main/java/com/momentive/backend/common/config/WebConfig.java`)의 CORS 설정에 `allowCredentials(true)` 추가.
- [x] 신규 `ErrorCode`(`VALIDATION_FAILED` 재사용, `EMAIL_ALREADY_EXISTS`, `INVALID_CREDENTIALS`, `INVALID_REFRESH_TOKEN`, `UNAUTHENTICATED`) 추가 및 `GlobalExceptionHandler` 매핑 확인.
- [x] `AuthService` 단위/통합 테스트: 회원가입 성공/중복이메일, 로그인 성공/실패(이메일없음·비번틀림 모두 동일 에러코드), refresh rotation 성공/재사용탐지, 로그아웃 후 refresh 실패 케이스.
- [x] 검증(자동): `./gradlew build`, `./gradlew test` 통과.

## Phase 2: 프론트 인증 인프라 (AuthProvider + apiFetch 401 refresh)

이 phase가 끝나면 화면 없이도 로그인 상태 전파 배선(Context, 쿠키 기반 `/me` 선호출, 401 자동 refresh)이 코드 레벨로 완결된 상태가 되고, 다음 phase는 이 위에서 UI만 붙이면 된다.

- [x] `src/lib/api/auth.ts` 신규: `signup`, `login`, `logout`, `refresh`, `me` — 백엔드 `/auth/*` 계약과 1:1, 모두 `apiFetch`(`src/lib/api/client.ts`) 경유.
- [x] `src/lib/api/client.ts`의 `apiFetch`에 401 자동 refresh + 1회 재시도 로직 추가. 동시 다중 요청이 401을 맞아도 refresh 호출은 in-flight promise 공유로 1회만 실행. refresh 실패 시 `ApiError(401)` 그대로 throw.
- [x] `AuthProvider`(Context, 위치는 `src/components/` 또는 `src/lib/auth/` 중 기존 구조에 맞는 곳) 신규: 로그인 사용자 정보(`id`, `email`, `nickname`) 상태, `login`/`logout` 함수 노출. 컴포넌트는 `auth.ts`를 직접 호출하지 않고 이 Provider를 통해서만 접근.
- [x] `src/app/(shell)/layout.tsx`(서버 컴포넌트)에서 요청 쿠키로 `/me`를 선호출해 `AuthProvider`의 초기값을 채움 — 로그인 상태 화면 깜빡임 최소화.
- [x] 타입: `User`(또는 `AuthUser`) 타입을 API 응답 계약에 맞게 명시, `any` 사용 금지.
- [x] 검증(자동): `npm run build`, `npm run lint` 통과.
- [x] 검증(수동/QA 성격 명시): 브라우저에서 로그인 없이 진입 시 `/me` 401 응답이 정상적으로 비로그인 상태로 이어지는지, 콘솔 에러 없이 렌더링되는지 확인. (E2E 시나리오 6: 비로그인 `/mypage` 진입 시 리다이렉트 없이 인라인 유도 UI 정상 노출로 `/me` 401 처리 확인. E2E 시나리오 7: 비로그인 `/`(shell 레이아웃 경유) 진입 시 콘솔 에러 0건 확인. 두 시나리오 조합으로 실질 커버.)

## Phase 3: 로그인/회원가입 화면

이 phase가 끝나면 사용자가 `/signup`에서 계정을 만들고 `/login`에서 로그인해 세션이 발급되는 흐름을 브라우저에서 끝까지 수행할 수 있는 상태가 된다.

- [x] `/signup` 페이지(`src/app/(shell)/signup/page.tsx` 또는 spec상 shell 예외 사유 없으므로 `(shell)` 하위): React Hook Form + Zod. 이메일 형식, 비밀번호 최소 8자+영문/숫자 조합, 닉네임 필수 클라이언트 검증. `TextField`/`PasswordField`(`src/components/forms/`) 사용, 없으면 신규 추가.
- [x] `/login` 페이지: 이메일/비밀번호 필드, 제출 버튼, "회원가입" 링크(`/signup`). 서버 `INVALID_CREDENTIALS`는 필드 지목 없이 폼 상단 또는 `Toast`(`src/components/feedback/Toast.tsx`)로 표시.
- [x] `/signup` 서버 에러 매핑: `ApiError.fieldErrors.email = EMAIL_ALREADY_EXISTS` 등을 RHF `setError("email", ...)`로 이메일 필드 아래 인라인 표시.
- [x] 회원가입/로그인 성공 시 `AuthProvider.login`을 통해 상태 갱신 후 마이페이지 또는 이전 화면으로 이동(라우팅 계약: spec 시나리오상 "마이페이지 또는 이전 화면").
- [x] 검증(자동): `npm run build`, `npm run lint` 통과.
- [x] 검증(수동, 브라우저): 신규 이메일로 회원가입 → 즉시 로그인 상태 확인, 동일 이메일 재가입 시 인라인 에러, 잘못된 비밀번호로 로그인 시 동일 에러 메시지 노출.

## Phase 4: 마이페이지 연동 + 기존 기능 회귀 확인

이 phase가 끝나면 마이페이지가 실제 로그인 상태를 반영하고, 로그아웃이 동작하며, 이번 변경이 기존 비로그인 허용 기능(상품 조회/장바구니/위시리스트)을 깨지 않았음이 확인된 상태가 된다.

- [x] `src/app/(shell)/mypage/page.tsx`의 프로필 영역(현재 36~38행 하드코딩 "몽이맘님")을 `AuthProvider` 상태 기반으로 조건 분기: 비로그인 시 "로그인이 필요합니다" 문구 + 로그인 버튼(→ `/login`, 로그인 후 마이페이지로 복귀), 로그인 시 실제 `nickname` 표시 + 로그아웃 버튼. 두 상태는 서로 배타적으로 렌더링되어야 함(`docs/backlog/2026-08-26-app-redesign-phase2-01.md` 사례 참고 — 조건에 겹침/누락 없는지 표로 확인).
- [x] 로그아웃 버튼 클릭 시 `AuthProvider.logout` 호출 → 서버 `/auth/logout` → 즉시 비로그인 UI로 전환.
- [x] 위시/장바구니 카운트 요약, 메뉴 리스트 등 마이페이지 나머지 UI는 최소 변경(프로필 영역만 교체) 유지.
- [x] 회귀 확인: 비로그인 상태에서 상품 목록/상세 조회, 장바구니 담기(`src/lib/storage/cart.ts`), 위시리스트 토글(`src/lib/storage/wishlist.ts`)이 기존과 동일하게 동작하는지 코드 경로상 이번 변경이 건드리지 않았음을 확인.
- [x] 검증(자동): `npm run build`, `npm run lint`, 백엔드 `./gradlew test` 통과(Phase 1~4 통합 상태 재확인).
- [x] 검증(수동, 브라우저): 비로그인으로 `/mypage` 진입 시 리다이렉트 없이 인라인 유도 UI 노출 → 로그인 버튼 클릭 → 로그인 → 마이페이지 복귀 → 닉네임 표시 확인 → 로그아웃 → 다시 인라인 유도 UI로 전환 확인.
