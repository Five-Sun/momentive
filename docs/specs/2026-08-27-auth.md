# 인증 (로그인/회원가입)

## 목적 (Why)

현재 마이페이지는 로그인 여부와 무관하게 하드코딩된 프로필("몽이맘님")을 보여주고, 위시리스트/장바구니/최근 본 상품은 전부 `localStorage` 기반이라 기기 간 동기화가 되지 않는다. 실제 계정을 만들어야 주문/결제 시 주문자 정보를 신뢰성 있게 다룰 수 있고, 마이페이지도 실사용자 데이터를 보여줄 수 있다. 이 spec은 이메일/비밀번호 기반 회원가입·로그인·로그아웃과 그에 필요한 세션(JWT) 관리를 도입해, 이후 결제 연동 spec이 실제 로그인 사용자를 전제로 진행될 수 있게 한다.

## 범위 (Scope)

### In Scope
- 이메일 + 비밀번호 회원가입/로그인/로그아웃
- JWT(Access 30분 + Refresh 14일, 사용 시마다 rotation) 기반 세션, httpOnly+Secure 쿠키(`SameSite=Lax`)
- Spring Security 도입, `@CurrentUser` 어노테이션으로 컨트롤러에 현재 로그인 사용자 주입
- `refresh_token` 테이블 도입 및 로그아웃/재사용 시 revoke
- `USER`/`ADMIN` 최소 role 구분 (admin 전용 API 자체는 범위 밖)
- 프론트 `/login`, `/signup` 화면 신규
- `AuthProvider`(Context)로 로그인 상태 전파, `(shell)/layout.tsx`에서 쿠키 기반 `/me` 선호출로 초기값 채움
- `apiFetch`의 401 자동 refresh + 1회 재시도, 동시 요청 시 refresh 1회 공유
- 마이페이지: 비로그인 시 인라인 "로그인 필요" 유도 UI(리다이렉트 아님), 로그인 시 실제 닉네임 표시, 로그아웃 버튼
- `WebConfig` CORS 설정에 `allowCredentials(true)` 추가

### Out of Scope
- 소셜 로그인(카카오/네이버/구글 등) — 별도 spec
- 이메일 인증(가입 확인 메일) — 이메일 발송 인프라 도입 시 별도 spec
- 비밀번호 찾기/재설정 — 위와 동일한 이유로 별도 spec
- 로그인 실패 횟수 제한, 계정 잠금, IP rate limiting
- 장바구니 담기/위시리스트 등 기존 비로그인 허용 기능을 로그인 필수로 전환하는 것 — 계속 비로그인 허용(localStorage 유지), 로그인 요구는 결제 시점부터(별도 spec)
- 재사용 가능한 공통 `<RequireAuth>` 래퍼 컴포넌트 — 보호가 필요한 화면이 마이페이지 하나뿐이라 페이지 내 조건부 렌더링으로 처리, 두 번째 사례가 생기면 그때 추출
- 휴대폰번호, 배송지 등 회원가입 시 추가 정보 수집 — 결제/주문 spec에서 다룸
- admin 전용 API 실제 기능

## 사용자 시나리오

### 1. 회원가입
1. `/signup`에서 이메일, 비밀번호, 닉네임을 입력한다.
2. 비밀번호는 최소 8자 + 영문/숫자 조합이 아니면 클라이언트 검증(Zod)에서 즉시 에러를 보여준다.
3. 제출 시 이메일이 이미 가입되어 있으면 서버가 필드 에러를 반환하고, 해당 이메일 입력란 아래 인라인으로 표시된다.
4. 성공하면 즉시 로그인 처리(Access/Refresh 쿠키 발급)되고 마이페이지 또는 이전 화면으로 이동한다. 별도 이메일 인증 절차는 없다.

### 2. 로그인
1. `/login`에서 이메일, 비밀번호를 입력한다.
2. 이메일이 존재하지 않거나 비밀번호가 틀리면 동일한 에러 메시지(계정 존재 여부를 노출하지 않음)를 폼 상단 또는 Toast로 보여준다.
3. 성공하면 Access/Refresh 쿠키가 발급되고 마이페이지 또는 이전 화면으로 이동한다.

### 3. 세션 유지 및 자동 갱신
1. 로그인 상태에서 Access Token이 만료된 뒤 API를 호출하면, `apiFetch`가 401을 감지해 자동으로 refresh를 시도하고 원요청을 1회 재시도한다.
2. 동시에 여러 요청이 401을 맞아도 refresh 호출은 한 번만 일어난다.
3. Refresh Token까지 만료/무효화된 상태면 refresh도 401로 실패하고, 클라이언트는 로그아웃 상태(비로그인)로 전환된다.

### 4. 로그아웃
1. 마이페이지의 로그아웃 버튼을 누르면 서버에 로그아웃 요청을 보내 해당 Refresh Token을 revoke하고, 쿠키를 만료시킨다.
2. 로그아웃 후 마이페이지는 비로그인 상태의 인라인 유도 UI로 즉시 전환된다.

### 5. 마이페이지 접근 (비로그인)
1. 로그인하지 않은 상태로 마이페이지 탭에 진입하면, 다른 화면으로 리다이렉트되지 않고 마이페이지 화면 안에서 "로그인이 필요합니다" 문구와 로그인 버튼을 보여준다.
2. 로그인 버튼을 누르면 `/login`으로 이동하고, 로그인 성공 후 마이페이지로 돌아온다.

### 6. 마이페이지 접근 (로그인됨)
1. 로그인한 상태로 마이페이지에 진입하면 하드코딩된 "몽이맘님" 대신 실제 로그인한 유저의 닉네임이 표시된다.
2. 위시/장바구니 카운트 요약, 메뉴 리스트 등 기존 UI는 그대로 유지된다.

## 인터페이스

### API

**`POST /auth/signup`**
- Request: `{ email: string, password: string, nickname: string }`
- Response 201: `{ id, email, nickname }` (Access/Refresh 쿠키를 `Set-Cookie`로 발급)
- 에러: `VALIDATION_FAILED`(400, 형식 오류 — `fieldErrors` 포함), `EMAIL_ALREADY_EXISTS`(409)

**`POST /auth/login`**
- Request: `{ email: string, password: string }`
- Response 200: `{ id, email, nickname }` (Access/Refresh 쿠키를 `Set-Cookie`로 발급)
- 에러: `INVALID_CREDENTIALS`(401) — 이메일 미존재/비밀번호 불일치 모두 동일 코드로 응답(계정 존재 여부 비노출)

**`POST /auth/logout`**
- 요청 쿠키의 Refresh Token을 조회해 revoke 처리
- Response 204, Access/Refresh 쿠키 만료 처리(`Set-Cookie`로 즉시 만료)
- 인증 안 된 상태로 호출해도 204로 무해하게 처리

**`POST /auth/refresh`**
- 요청 쿠키의 Refresh Token으로 새 Access/Refresh Token 발급(rotation, 기존 Refresh Token은 무효화)
- Response 200: 빈 바디 또는 `{ id, email, nickname }` (Access/Refresh 쿠키를 `Set-Cookie`로 갱신)
- 에러: `INVALID_REFRESH_TOKEN`(401) — 만료/무효화/재사용 탐지 시

**`GET /auth/me`**
- 요청 쿠키의 Access Token으로 현재 로그인 사용자 조회
- Response 200: `{ id, email, nickname }`
- 에러: `UNAUTHENTICATED`(401) — 쿠키 없음/Access Token 만료·무효

### 화면

**`/login`**
- 이메일/비밀번호 `TextField`/`PasswordField`, 제출 버튼, "회원가입" 링크(→ `/signup`)
- 서버 에러(`INVALID_CREDENTIALS`)는 폼 상단 또는 Toast로 표시(특정 필드 지목 없이)

**`/signup`**
- 이메일/비밀번호/닉네임 필드, 제출 버튼, "로그인" 링크(→ `/login`)
- 클라이언트 검증(Zod): 이메일 형식, 비밀번호 최소 8자+영문/숫자 조합, 닉네임 필수
- 서버 `fieldErrors.email = EMAIL_ALREADY_EXISTS` 등은 이메일 필드 아래 인라인 표시

**마이페이지 (`/mypage`) 변경**
- 비로그인 상태: 기존 프로필 영역을 "로그인이 필요합니다" 문구 + 로그인 버튼으로 대체. 위시/장바구니/메뉴 등 나머지는 기존 그대로 유지할지 여부는 구현 시 최소 변경(프로필 영역만 교체)으로 처리
- 로그인 상태: 프로필 영역에 실제 닉네임 표시, 로그아웃 버튼 추가

### 데이터 모델

**`User`**
- `id` (PK)
- `email` (unique, not null)
- `password_hash` (not null, BCrypt)
- `nickname` (not null, unique 아님)
- `role` (`USER` | `ADMIN`, default `USER`)
- `created_at`

**`refresh_token`**
- `id` (PK)
- `user_id` (FK → User)
- `token_hash` (실제 토큰 값은 해싱해 저장)
- `expires_at`
- `revoked_at` (nullable — revoke 시점 기록)
- `created_at`

## 수용 기준 (Acceptance Criteria)

- [ ] 이메일/비밀번호/닉네임으로 회원가입하면 계정이 생성되고 즉시 로그인 상태(Access/Refresh 쿠키 발급)가 된다
- [ ] 이미 가입된 이메일로 회원가입하면 `EMAIL_ALREADY_EXISTS` 필드 에러가 이메일 입력란에 표시된다
- [ ] 비밀번호가 8자 미만이거나 영문/숫자 조합이 아니면 클라이언트에서 제출 전에 에러가 표시된다
- [ ] 올바른 이메일/비밀번호로 로그인하면 Access/Refresh 쿠키가 발급되고 마이페이지에서 로그인 상태가 반영된다
- [ ] 틀린 비밀번호 또는 존재하지 않는 이메일로 로그인하면 동일한 `INVALID_CREDENTIALS` 에러가 표시된다(계정 존재 여부가 구분되지 않음)
- [ ] Access Token 만료 후 API 호출 시 자동으로 refresh되어 원요청이 재시도되고, 사용자는 로그아웃되지 않는다
- [ ] 동시에 여러 요청이 401을 맞아도 `/auth/refresh` 호출은 한 번만 발생한다
- [ ] Refresh Token이 만료/무효화된 상태에서는 refresh도 실패하고 클라이언트가 비로그인 상태로 전환된다
- [ ] 로그아웃하면 서버의 해당 Refresh Token이 revoke되고, 쿠키가 만료되며, 마이페이지가 즉시 비로그인 UI로 전환된다
- [ ] 비로그인 상태로 마이페이지에 진입하면 리다이렉트 없이 인라인으로 "로그인이 필요합니다" + 로그인 버튼이 보인다
- [ ] 로그인 상태로 마이페이지에 진입하면 하드코딩된 닉네임 대신 실제 로그인한 유저의 닉네임이 표시된다
- [ ] 비로그인 상태에서도 상품 조회/장바구니 담기/위시리스트 토글은 기존과 동일하게 동작한다(회귀 없음)
- [ ] `WebConfig`의 CORS 설정에 `allowCredentials(true)`가 추가되어 쿠키 기반 인증 요청이 정상 동작한다
