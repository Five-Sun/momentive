# E2E 케이스 작성 규격

`plan`의 마지막 코드 phase가 통과된 뒤, `e2e-tester` 에이전트가 유저 플로우 관점의 통합테스트 시나리오를 기록하는 문서의 규격이다. `docs/specs/`, `docs/plans/`와 명명 관례를 통일하고, 시나리오 설명(사람이 읽는 문서)과 실행 스크립트([dev-browser](https://github.com/sawyerhood/dev-browser)에 넘길 JS)를 한 파일에 함께 담는다.

## 파일 위치 및 이름

```
docs/e2e/YYYY-MM-DD-<feature-slug>.md
```

- `YYYY-MM-DD`: e2e-tester가 케이스를 생성한 날짜
- `<feature-slug>`: 기반 spec/plan과 동일한 slug
- 같은 feature를 나중에 다시 검증해 시나리오가 늘거나 바뀌면, 기존 파일은 수정하지 않고 새 날짜로 새 파일을 추가한다 (spec과 동일한 이력 누적 방식). spec의 `supersedes`와 달리 이전 파일이 "대체"되는 게 아니라 회귀 대상으로 계속 유효하므로, `supersedes` 필드는 두지 않는다.

## Frontmatter

```yaml
---
date: YYYY-MM-DD
feature: <feature-slug>
spec: <근거 spec 파일명>
plan: <근거 plan 파일명>
---
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `date` | string (`YYYY-MM-DD`) | 필수 | 생성된 날짜, 파일명의 날짜와 동일 |
| `feature` | string (kebab-case) | 필수 | 파일명의 slug와 동일. **plan의 frontmatter `feature:`를 그대로 쓴다** (plan이 참조하는 spec의 `feature:`와 다를 수 있음 — plan-runner/reviewer가 호출 시 쓰는 `feature-slug`와 일치시켜야 `docs/e2e/*-<feature-slug>.md` 검색이 맞물린다) |
| `spec` | string (파일명) | 필수 | 케이스 도출 근거가 된 spec 파일명 |
| `plan` | string (파일명) | 필수 | 이 케이스를 요구한 plan 파일명 |

## 본문 섹션

파일 상단에 `# <기능명> E2E 케이스` 제목을 두고, 그 아래 시나리오별로 `## 시나리오 N: <이름>` 섹션(설명 전용, 코드 없음)을 반복한 뒤, 맨 마지막에 전체 시나리오를 순서대로 이어 실행하는 단일 스크립트를 담은 `## 실행 스크립트` 섹션을 둔다. **한 파일 = 한 유저 플로우 = 한 탭(page)**이 원칙이다 — dev-browser는 CLI 호출이 끝나도 브라우저를 띄운 채 유지하는 영속 데몬이라, 시나리오마다 새 이름으로 탭을 열면 탭이 계속 쌓인다.

```markdown
## 시나리오 N: <시나리오 이름>

<spec 사용자 시나리오/AC의 어느 부분에서 도출했는지, 무엇을 검증하는지 한두 문장>

**사전조건**: <이 시나리오 실행 전 필요한 상태. 파일 내 앞선 시나리오가 만든 상태(로그인, 장바구니 등)를 그대로 이어받는 게 기본이므로, 그걸로 충족되면 "앞 시나리오 상태로 충족"이라고 적는다. 앞 시나리오와 무관하게 추가로 필요한 상태만 명시>

**판정 기준**: <무엇을 만족하면 pass인지 — 화면 텍스트, 라우팅 경로, 요소 노출 여부 등을 구체적으로>
```

```markdown
## 실행 스크립트

\`\`\`javascript
const page = await browser.getPage("<feature-slug>");
await page.goto("http://localhost:3000/...", { waitUntil: "domcontentloaded" });

// --- 시나리오 1 ---
// ... 진행 스텝
if (!(await page.locator("...").isVisible())) {
  throw new Error("시나리오 1 판정 기준 미충족: ...");
}
console.log("PASS: 시나리오 1");

// --- 시나리오 2 ---
// 앞 시나리오가 만든 상태(로그인 세션, 라우팅 등)를 그대로 이어받아 진행
// ...
console.log("PASS: 시나리오 2");

// (이하 시나리오 순서대로 반복)
\`\`\`
```

- 스크립트는 dev-browser CLI(`dev-browser <<'EOF' ... EOF`)에 그대로 붙여넣을 수 있는 완결된 형태로, **파일 전체를 하나의 dev-browser 실행 단위**로 작성한다 — 시나리오마다 별도로 실행하지 않는다. 기본값은 headed 모드(브라우저 창이 화면에 보임) — 사용자가 진행 상황을 육안으로 확인해 수동 테스트/디버깅 부담을 줄이는 것이 이 도구의 목적이기 때문이다.
- `browser.getPage(name)`는 스크립트 맨 앞에서 파일당 한 번만 호출한다 (`name`은 `<feature-slug>` 하나로 고정). 이후 모든 시나리오는 이 `page` 하나를 순서대로 재사용해, 실제 유저가 화면을 옮겨가는 것과 같은 흐름으로 진행한다.
- 판정은 시나리오마다 `console.log("PASS: 시나리오 N")`으로 표시하고, 실패는 시나리오 번호를 메시지에 포함한 `throw`로 알린다. **하나의 시나리오가 throw하면 스크립트 전체가 그 자리에서 중단되고 이후 시나리오는 실행되지 않는다** — 같은 탭에서 이어지는 흐름이므로 앞 단계가 깨진 채로 뒤 단계를 진행해봐야 결과가 무의미하기 때문에 의도된 동작이다(try/catch로 감싸 계속 진행하지 않는다). e2e-tester는 미실행된 시나리오를 "실패"가 아니라 "앞 시나리오 실패로 미실행"으로 구분해 보고한다.
- 실패 시 스크린샷은 `saveScreenshot(buf, name)`으로 저장한다 — dev-browser의 파일 I/O는 `~/.dev-browser/tmp/`로 제한되므로, 저장된 실제 경로는 스크립트 실행 결과(stdout)에서 확인하고 e2e-tester가 이를 읽어 backlog 문서에 인용한다. 파일명에 시나리오 번호를 포함해(`<feature-slug>-scenario-N-...`) 어느 단계에서 실패했는지 구분한다.
- **셀렉터**: 프론트엔드 코드에 `data-testid`가 없는 한(기본값으로 존재를 가정하지 않는다), Playwright의 role/text 기반 로케이터(`getByRole`, `getByText`, `getByPlaceholder` 등 spec의 화면 요구사항에 실제로 등장하는 문자열/역할)를 우선 사용한다. 케이스 생성 시 대상 컴포넌트 파일을 Read/Grep으로 확인해 실제 마크업(태그, aria 속성, 표시 텍스트)에 맞는 로케이터를 쓴다 — 추측이나 존재하지 않는 속성으로 셀렉터를 지어내지 않는다. role/text로 안정적으로 특정할 수 없는 요소(예: 반복 렌더링되는 카드 컨테이너처럼 텍스트가 매번 달라지는 경우)는 실제 컴포넌트의 className을 근거로 한 CSS 셀렉터를 fallback으로 쓰되, 시나리오 설명에 "CSS 셀렉터 fallback 사용, 컴포넌트 구조 변경 시 갱신 필요"라고 남긴다.
- **시나리오 순서와 상태 충돌**: 시나리오는 실제 유저가 화면을 옮겨가는 순서, 즉 spec "사용자 시나리오"의 단계 순서를 기본 배치로 삼는다. 뒤 시나리오의 사전조건이 앞 시나리오가 만든 상태와 어긋나면(예: 앞에서 로그인했는데 뒤에서는 비로그인 상태가 필요, 또는 앞에서 장바구니에 담았는데 뒤에서는 빈 장바구니가 필요), 화면 조작(로그아웃, 항목 삭제 등)으로 스크립트 안에서 명시적으로 상태를 되돌리고 순서를 유지한다. 화면에 되돌릴 수단이 없어 정말 독립된 초기 상태가 필요한 시나리오(예: DB가 완전히 비어 있어야 함)는 같은 파일/탭에 억지로 넣지 말고 별도의 `docs/e2e/YYYY-MM-DD-<feature-slug>-<sub-slug>.md` 파일로 분리해 별도 탭으로 실행한다. 그마저도(시드 스크립트 부재 등으로) 실행 시점에 상태를 만족시킬 방법이 없으면 해당 시나리오는 실행하지 않고 "사전조건 미충족으로 스킵"이라고 보고한다 — 실패로 잘못 판정하지 않는다.

## 케이스 도출 기준

- 1차 근거: 대상 spec의 "사용자 시나리오" 섹션 각 단계, "수용 기준(AC)" 각 항목
- 보조 참고: 실제 구현된 라우트/컴포넌트/API — spec에 없던 예외 케이스(예: 빈 장바구니, 재고 없음)가 코드에 존재하면 시나리오로 추가할 수 있다
- 이번 plan에서 새로 추가/변경된 시나리오만 대상으로 한다. 기존에 이미 다른 `docs/e2e/*.md`에 있는 시나리오를 다시 반복해서 만들지 않는다.

## 작성 주체 및 시점

`e2e-tester` 에이전트가 자신이 호출된 시점(plan의 마지막 코드 phase 통과 직후)에 대상 spec을 읽고 그 자리에서 생성한다. plan에는 미리 존재하지 않으며, planner가 만들지 않는다.

## 조회 방법

전체 회귀를 실행할 때는 `docs/e2e/*.md` 전체를 대상으로 하고, 특정 feature의 이력만 볼 때는 다음으로 훑는다.

```bash
ls docs/e2e/*-<feature-slug>.md
```
